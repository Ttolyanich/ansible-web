## 1. Архитектура, база данных и многопоточность

### 1.1. Рассинхронизация воркеров Gunicorn и фоновых задач (Критичность: ВЫСОКАЯ)
* **Локация:** `docker-compose.yml` (строка 15), `task_engine.py` (строки 18–37)
* **Суть проблемы:**  
  В `docker-compose.yml` приложение запускается через:
  ```bash
  gunicorn --workers 2 --threads 4 ... app:app
  ```
  При этом процессы задач и пул зарегистрированы в памяти одного конкретного процесса:
  ```python
  executor = ThreadPoolExecutor(max_workers=4)
  active_task_processes: Dict[int, subprocess.Popen] = {}
  ```
  Воркеры Gunicorn изолированы друг от друга. Если запуск задачи произошел в воркере #1, а запрос отмены `POST /tasks/<id>/cancel` обработал воркер #2, отмена **не сработает**, так как во втором процессе словарь `active_task_processes` пуст.
* **Решение:**
  1. До перехода на внешнюю очередь задач зафиксировать в Gunicorn: `--workers 1 --threads 8` (один процесс, много потоков).
  2. В целевой архитектуре вынести выполнение задач в отдельный фоновый воркер (Celery / RQ / Redis).

---

### 1.2. Дублирование планировщика APScheduler в каждом воркере (Критичность: ВЫСОКАЯ)
* **Локация:** `app.py` (строки 65–75)
* **Суть проблемы:**  
  Инициализация `scheduler.start()` выполняется при импорте `app.py`. При наличии 2 воркеров запускаются 2 параллельных таймера. Каждый час оба процесса одновременно начинают выгрузку 600+ серверов из Zabbix в SQLite, создавая взаимоблокировки и двойную нагрузку на Zabbix API.
* **Решение:**  
  Инициализировать планировщик только в выделенном процессе/контейнере или защитить его выполнение межпроцессным lock-файлом (`fcntl.flock` на Linux).

---

### 1.3. Блокировки SQLite (`database is locked`) и хранение тяжелых логов (Критичность: ВЫСОКАЯ)
* **Локация:** `app.py` (строка 32), `models.py` (строки 246–247), `task_engine.py` (строки 924–929)
* **Суть проблемы:**  
  1. В SQLite по умолчанию используется режим журнала `DELETE`, где любая запись монопольно блокирует всю базу для чтения.
  2. Во время работы плейбука `task_engine.py` каждые 800 мс перезаписывает всё поле `task.log_output` (размером до 5–15 МБ на 600 серверов) и делает `db.session.commit()`. Это регулярно вызывает 500-е ошибки `sqlite3.OperationalError: database is locked`.
* **Решение:**
  1. Включить режим **WAL (Write-Ahead Logging)** и таймаут ожидания 30 сек:
     ```python
     from sqlalchemy import event
     @event.listens_for(db.engine, "connect")
     def set_sqlite_pragma(dbapi_connection, connection_record):
         cursor = dbapi_connection.cursor()
         cursor.execute("PRAGMA journal_mode=WAL")
         cursor.execute("PRAGMA synchronous=NORMAL")
         cursor.execute("PRAGMA busy_timeout=30000")
         cursor.close()
     ```
  2. Стриминг логов писать в плоские файлы `/app/instance/tasks/{task_id}.log`, а в БД сбрасывать только финальный статус и итоговый Play Recap.
  3. В перспективе — миграция на PostgreSQL (`postgres:16-alpine` в Docker Compose).

---

### 1.4. Проблема N+1 SQL-запросов (Критичность: СРЕДНЯЯ)
* **Локация:** `app.py` (строка 197), `templates/hosts.html` (строки 151–225), `templates/user_ops.html` (строка 104)
* **Суть проблемы:**  
  При открытии `/hosts` на 600 серверов выполняется более 1200 дополнительных SQL-запросов для получения `host.group.name` и `host.override_credential.name`.
* **Решение:**  
  Использовать Eager Loading:
  ```python
  from sqlalchemy.orm import joinedload
  hosts = query.options(
      joinedload(Host.group),
      joinedload(Host.override_credential)
  ).order_by(Host.name).all()
  ```

## 2. Информационная безопасность

### 2.1. Публичный дефолтный Fernet-ключ (Критичность: КРИТИЧЕСКАЯ)
* **Локация:** `docker-compose.yml` (строка 11), `models.py` (строка 33)
* **Суть проблемы:**  
  В коде захардкожен ключ:
  ```
  v1tX7e1eHnZtTqK_x6FvE9qL1pG2bA4sD6jK8mN0wQY=
  ```
  Если `.env` не настроен или скопирован из примера, любой, получивший файл `ansible_web.db`, расшифрует все root-пароли, приватные SSH-ключи и токен Zabbix.
* **Решение:**  
  Удалить дефолтный ключ из Compose и кода. При отсутствии `FERNET_KEY` в окружении генерировать уникальный ключ в локальный файл `instance/fernet.key` с правами `0600`. На боевом сервере сменить ключ и перешифровать креды.

---

### 2.2. Отсутствие CSRF-защиты (Критичность: КРИТИЧЕСКАЯ)
* **Локация:** Все формы (`app.py`, `templates/`)
* **Суть проблемы:**  
  POST-маршруты управления учетными записями, перезапуска сервисов и сохранения плейбуков не защищены CSRF-токенами. При переходе авторизованного админа по внешней ссылке злоумышленник может инициировать запуск плейбука или создание пользователя.
* **Решение:**  
  Подключить `Flask-WTF` с глобальным `CSRFProtect(app)` и вставить `{{ csrf_token() }}` во все формы.

---

### 2.3. Внедрение shell-команд через Jinja2 (Критичность: КРИТИЧЕСКАЯ)
* **Локация:** `playbooks/user_create.yml` (строка 32), `playbooks/service_restart.yml` (строка 22)
* **Суть проблемы:**  
  Прямая конкатенация переменных в shell:
  ```yaml
  echo "{{ u.username }}:{{ u.password }}" | chpasswd ...
  ```
  Если пароль содержит одинарную кавычку `'` (например, `P@ss'word`), команда shell разрывается, что приводит к синтаксическому сбою или выполнению сторонней команды.  
  В `service_restart.yml`: команда `systemctl is-active {{ target_service }}` уязвима к передаче имени сервиса с разделителями команд.
* **Решение:**  
  1. В `app.py` валидировать `username` и `target_service` по белым спискам символов (regex `^[a-zA-Z0-9_.-]+$`).
  2. Пароли передавать не через shell-строку, а генерировать хэш (`password_hash('sha512')`) на контроллере и передавать через безопасные модули или экранированные переменные.

---

### 2.4. Редактирование системных плейбуков операторами (Критичность: ВЫСОКАЯ)
* **Локация:** `app.py` (строки 949–995)
* **Суть проблемы:**  
  Маршрут `/playbooks/save` доступен любому вошедшему пользователю (нет `@admin_required`). Проверка системных файлов запрещает только **смену имени**, но позволяет **перезаписать тело** системного плейбука (например, внедрить бэкдор в `host_bootstrap.yml`).
* **Решение:**  
  1. Наложить `@admin_required` на сохранение/удаление плейбуков.
  2. Полностью заблокировать сохранение системных файлов через веб-интерфейс (`if filename in SYSTEM_PLAYBOOKS: abort(403)`).

---

### 2.5. Небезопасные права на временные файлы Ansible (Критичность: ВЫСОКАЯ)
* **Локация:** `ansible.cfg` (строка 9)
* **Суть проблемы:**  
  Опция `allow_world_readable_tmpfiles = True` позволяет любым локальным пользователям серверов читать временные файлы скриптов и переданных секретов.
* **Решение:**  
  Выставить `allow_world_readable_tmpfiles = False` и настроить POSIX ACL на целевых хостах.

## 3. Отказоустойчивость и безопасность инфраструктуры

### 3.1. Ложный статус выполнения задач (`failed_when: false`) (Критичность: ВЫСОКАЯ)
* **Локация:** `playbooks/user_create.yml` (строка 125)
* **Суть проблемы:**  
  В блоке провижининга выставлено `failed_when: false`. Если диск переполнен, `/etc/passwd` недоступен или упал синтаксис — задача возвращает зеленый статус «Успешно». Инженер уверен, что доступ выдан, хотя учетка не создана.
* **Решение:**  
  Проверять наличие контрольного маркера в выводе:
  ```yaml
  failed_when: "'USER_' + u.username + '_CONFIGURED' not in linux_provision_res.stdout"
  ```

---

### 3.2. Риск бана контроллера в fail2ban при автоподборе кредов (Критичность: ВЫСОКАЯ)
* **Локация:** `task_engine.py` (строки 820–827)
* **Суть проблемы:**  
  Параметр `max_passes = 6` запускает до 6 попыток авторизации подряд с перебором разных профилей и паролей. Это гарантированно исчерпывает лимит `fail2ban` (обычно 3–5 попыток) и приводит к блокировке управляющего IP на клиентских серверах.
* **Решение:**  
  Ограничить число проходов до 2 (основной профиль + системный дефолт) либо добавить явный переключатель агрессивного перебора.

---

### 3.3. Риск удаления рабочих томов в `docker_cleanup.yml` (Критичность: КРИТИЧЕСКАЯ)
* **Локация:** `playbooks/docker_cleanup.yml` (строка 16)
* **Суть проблемы:**  
  Команда:
  ```bash
  docker system prune -f --volumes
  ```
  Флаг `--volumes` безвозвратно удаляет **все неиспользуемые тома**. Если во время запуска сценария контейнер с базой данных (Postgres, MySQL, Redis) был временно остановлен, том с боевыми данными будет удален.
* **Решение:**  
  Убрать `--volumes` из стандартного плейбука обслуживания: `docker system prune -f`.

---

### 3.4. Случайная подмена IP-адресов из комментариев Zabbix (Критичность: СРЕДНЯЯ)
* **Локация:** `zabbix_client.py` (строки 40–46)
* **Суть проблемы:**  
  Если комментарий в Zabbix содержит произвольный IP (например: `DNS 8.8.8.8, шлюз 192.168.1.1`), алгоритм берет первый попавшийся адрес и назначает его как целевой `ip_address` хоста.
* **Решение:**  
  Извлекать IP строго при наличии явных маркеров (`vpn:`, `wg:`, `tunnel:`, `ip:`) и отключить слепой поиск любого IPv4.

## 4. Плейбуки и специфика автоматизации

### 4.1. Специфика подхода `raw` и кроссплатформенность
* **Плюсы `raw`:** Выполнение за 1 SSH-сеанс решает проблему `ufw limit 22/tcp`, работает без установленного Python.
* **Недостатки и баги:**
  1. В `user_create.yml` для добавления групп используется `usermod -a -G sudo`. В Alpine Linux нет `usermod` (нужно `addgroup <user> sudo`).
  2. В `host_bootstrap.yml` (строка 146) запись публичного ключа выполнена через `>` вместо `>>`:
     ```bash
     echo "{{ u.ssh_key }}" > "/home/{{ u.username }}/.ssh/authorized_keys"
     ```
     Это затирает все существующие ключи пользователя.

## 5. Фронтенд, производительность и UX

### 5.1. Использование Tailwind Play CDN в продакшне (Критичность: СРЕДНЯЯ)
* **Локация:** `templates/base.html` (строка 11)
* **Суть проблемы:**  
  Play CDN компилирует CSS на лету в браузере при каждом открытии страницы, что приводит к задержкам рендеринга и мерцанию стилей.
* **Решение:**  
  Собрать статический CSS файл через Tailwind CLI и раздавать локально через Nginx.

---

### 5.2. Отсутствие пагинации в таблице на 600+ хостов (Критичность: СРЕДНЯЯ)
* **Локация:** `templates/hosts.html`
* **Суть проблемы:**  
  Таблица генерирует огромный DOM-документ (1.5–2 МБ HTML), что замедляет работу на мобильных устройствах и слабых ПК.
* **Решение:**  
  Добавить серверную пагинацию (по 50/100 серверов) средствами Flask-SQLAlchemy `paginate()`.
